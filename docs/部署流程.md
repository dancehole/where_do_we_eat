# 部署流程（吃饭页新功能 + 日常热更新）

本文记录「去哪儿吃饭」项目的完整部署流程：**本地构建前端 → 上传 GitHub → 传输到远端 `dancehole@192.168.31.5` → 重启服务**。
其中「地址附近筛选 / 想去的品牌强制展示 / 美食地图」等新功能已并入主分支，按本流程部署即可生效。

---

## 0. 关键事实（部署前必读）

- **远端路径**：`/home/dancehole/project/where_do_we_go_to_eat`（用户 home 为 `dancehole`）。
- **远端环境**：Ubuntu 20.04，Node `v24`（在 `~/.local/bin`），Python venv 在 `backend/.venv`，glibc `2.31`。
- **远端无法自己构建前端**：Taro 3.6 构建要求 glibc ≥ 2.32，远端 `2.31` 不满足 → **前端 `dist` 必须在本地用 Node 20 构建后传上去**，不要指望远端 `npm run build`。
- **远端是一份手动部署的旧项目**（本地 git 仓库无提交），因此**不能靠远端 `git pull` 同步**，需「本地远程传输」。
- **千万别覆盖远端这三样**：`backend/.env`（密钥/高德 Key/数据库密码）、`certs/`（TLS 证书）、`*.db`（数据库）。传输时一律排除。
- **端口**：后端 `:8000`、前端静态 `:3000`、HTTPS 同源 `:8443`（精确定位走这个）。

## 1. 本地构建前端（Node 20）

> 必须在**有 Node 20 的机器**上构建；Node 22 在部分环境下也可，但 Node 20 最稳。

```bash
cd frontend
# 构建期会从 backend/.env 注入高德 JS Key（不入库明文），确保 backend/.env 存在
export PATH="/d/DevEnv/nodeDev/nvm/nvm/v20.18.3:$PATH"   # 示例：本机 Node 20 路径
export HOME="/c/Users/13917"
export APPDATA="C:/Users/13917/AppData/Roaming"          # Windows 下 Taro CLI 需要
node node_modules/@tarojs/cli/bin/taro build --type h5
# 产物在 frontend/dist/
```

产物即 `frontend/dist/`，后面整体传到远端覆盖旧的 `dist`。

## 2. 推送到 GitHub

```bash
git add -A
git commit -m "feat: ..."
git push origin main
```

> 若本机 SSH 到 github 异常（如某些 shell 下原生 `C:\Windows\System32\OpenSSH\ssh.exe` 无输出/255），
> 改用 Git 自带的 `/usr/bin/ssh`：
> ```bash
> export GIT_SSH_COMMAND="/usr/bin/ssh -o StrictHostKeyChecking=no -o UserKnownHostsFile=NUL"
> git push origin main
> ```

## 3. 部署到远端（本地远程传输，免 rsync）

远端没装 rsync 客户端（本地也没有），用 `tar` 通过 SSH 管道传输，既快又能精确排除敏感目录。
下面两条命令在**本地项目根目录**执行。

### 3.1 传输源码（排除 dist / .env / certs / venv / db / logs / node_modules）

```bash
SSH="/usr/bin/ssh -o StrictHostKeyChecking=no -o UserKnownHostsFile=NUL -o ConnectTimeout=20"
REMOTE="dancehole@192.168.31.5"
DEST="/home/dancehole/project/where_do_we_go_to_eat"

cd /e/code/3_MY_Github/where_do_we_go_to_eat
tar czf - \
  --exclude=.git --exclude=node_modules --exclude='*.db' --exclude='*.sqlite*' \
  --exclude=logs --exclude='*.log' --exclude=certs --exclude='.env' --exclude='*/.env' \
  --exclude=__pycache__ --exclude='*.pyc' --exclude='.venv' --exclude=frontend/dist \
  --exclude=.workbuddy . \
  | $SSH $REMOTE "cd $DEST && tar xzf -"
```

这会覆盖后端的 `app/`、前端的 `src/`、配置、`docs/`、`deploy/` 等，**不会动** `.env`/`certs`/`*.db`/`.venv`/`node_modules`。
（慢速链路下整包传输约 8–10 分钟，属正常。）

### 3.2 传输构建产物 dist（先清后传，避免旧 chunk 残留）

```bash
$SSH $REMOTE "rm -rf $DEST/frontend/dist && mkdir -p $DEST/frontend/dist"
cd /e/code/3_MY_Github/where_do_we_go_to_eat/frontend/dist
tar czf - . | $SSH $REMOTE "cd $DEST/frontend/dist && tar xzf -"
```

## 4. 热更新重启服务

远端用 `run_server.sh` 管理：`fuser -k` 释放 3000/8000/8443 端口，再用 `setsid` 后台拉起后端(uvicorn) + 前端(serve.js) + HTTPS(https_server.js)。
**后端代码/前端 dist 传完后，到远端执行一次即可热更新**：

```bash
$SSH $REMOTE "cd $DEST && bash run_server.sh"
```

- 脚本自带 `fuser -k 3000/tcp 8000/tcp 8443/tcp`，会先杀旧进程再起新的，不会端口冲突。
- 若只改了后端 Python：kill 8000 即可；但用 `run_server.sh` 一把梭最省心。
- 想只重启某一项也可手动 `fuser -k 8000/tcp` 后单独起 uvicorn。
- 若远端用 systemd（见 `deploy/systemd/`）：`systemctl restart where-eat-backend where-eat-frontend where-eat-https`。

> 后端本次新增字段（`near_lat/near_lng/near_addr/want`）只是**查询参数**，不新增数据库列，无需跑迁移。

## 5. 验证

```bash
# 后端存活
curl -s -o /dev/null -w "%{http_code}\n" http://192.168.31.5:8000/

# 新筛选参数是否生效（随便一个碰面码；这里只验证接口不报错、返回列表）
# 地址附近：传 near_lat/near_lng 作为检索中心
# 想去的品牌：传 want=品牌名，无视距离强制返回
curl -s "http://192.168.31.5:8000/api/meetups/<CODE>/restaurants?want=海底捞&near_lat=31.23&near_lng=121.47" \
  -H "X-Device-Id: test-device" | head -c 800

# 看后端日志
$SSH $REMOTE "tail -n 40 $DEST/backend/logs/backend.log"
```

预期：返回 JSON 数组；若传了 `want`，结果里至少包含一个 `reason` 含「你想吃」的餐厅；若传了 `near_*`，检索以该坐标为中心。

前端访问：
- 局域网：`http://192.168.31.5:3000/`（接口自动走 `:8000`）
- 精确定位（安全上下文）：`https://192.168.31.5:8443/`（需设备安装 `certs/ca.crt`）

## 6. 排错速查

| 现象 | 处理 |
| --- | --- |
| 前端地图空白 | 检查 `backend/.env` 的 `AMAP_JS_KEY`，构建时已注入；浏览器控制台看 `[Map]` 日志 |
| 接口 401 | 请求头缺 `X-Device-Id`，前端自动带，curl 测试需手动加 |
| 远端拉不起后端 | `tail backend/logs/backend.log`；多为 `.env` 缺失或 venv 路径 |
| 旧 chunk 仍被加载 | 重新执行 3.2（清 dist 再传），并硬刷新浏览器 |
| HTTPS 打不开 | 确认远端 `certs/server.crt` 与 `certs/server.key` 存在，否则 `run_server.sh` 会跳过 HTTPS |
