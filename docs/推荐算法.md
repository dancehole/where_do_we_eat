## 一、调用哪些接口

| 环节       | 接口                                                 | 说明                                   |
| ---------- | ---------------------------------------------------- | -------------------------------------- |
| 前端页面   | `GET /api/meetups/{code}/restaurants`                | 唯一入口，`price_max` 等筛选作为 query |
| （需要时） | `GET /api/meetups/{code}/center`                     | 详情页「算中心点」                     |
| 设置偏好   | `POST /api/meetups/{code}/preferences`               | ⚠️ 前端**从未调用**（无 UI）            |
| AI 推送    | `POST /api/ai/recommend`                             | 点「AI 推送」按钮才走                  |
| **外部**   | 高德 `https://restapi.amap.com/v3/place/around`      | 餐厅主数据源                           |
| **外部**   | DeepSeek `https://api.deepseek.com/chat/completions` | OpenAI 兼容，仅 AI 推送用              |

## 二、中心点怎么来（`_ensure_center`）

- **同城**（任意两人距离都 < 30km）：球面几何**质心** `centroid`（三维坐标平均，比经纬度直接平均准）
- **跨城**：`equal_cost_center` 从质心出发做**三级网格搜索**（步长 2 → 0.5 → 0.125），使每个人的交通距离**方差最小**（大家花的路费尽量一样多）
- 只算一次，之后**持久化到 meetup**（位置快照）

## 三、取餐厅数据（`amap.search_restaurants`）

以中心点做**周边检索**：`radius=3000`、`keywords=餐厅`、`types=餐饮服务`、`extensions=all`、`sortrule=weight`，**只取 1 页、最多 25 条**。

解析出的字段：名称、坐标、地址、`category`（高德完整品类串，如 `餐饮服务;中餐厅;火锅店`）、`cuisine`（取品类串**最后一段**＝最细品类）、`avg_price`（`biz_ext.cost`）、`rating`（`biz_ext.rating`）、`distance`（距中心米数）、`business_area`、`near_subway`。

> 无 Key 或请求失败 → 用 `_mock_restaurants()` 的 10 条假数据兜底（前端会看到 `source: "mock"`）。

## 四、排序算法（`rank.score_restaurants`，满分 100）

默认权重：**评分 0.35 / 价格 0.25 / 交通 0.20 / 菜系 0.15 / 距离 0.15**。逐家算分：

| 项         | 规则                                                        | 分值                         |
| ---------- | ----------------------------------------------------------- | ---------------------------- |
| **硬排除** | 店名命中 `restaurant_exclude` 或 `brand_exclude`            | 直接丢弃（不进结果）         |
| 优先加分   | 命中 `brand_include` / `restaurant_include`                 | **+12** / **+10**            |
| 菜系匹配   | 筛选的 categories 命中 `category`                           | +15（`w.category×100`）      |
| 评分       | `(rating/5) × 0.35 × 100`                                   | 0–35（5 星满分）             |
| 价格       | 低于下限/高于上限                                           | **−12**                      |
| 价格       | 在预算内 → `0.25×100×(1 − |price−price_max|/(price_max+1))` | 0–25，**越贴近预算上限越高** |
| 交通       | 筛了「近地铁」且高德有 subway 字段                          | +10                          |
| 交通       | 筛了「近商圈」且有商圈                                      | +10                          |
| 距离       | `0.15×100×(1 − min(dist/radius,1))`                         | 0–15，越近越高               |

最后 `score = clamp(0, 100)`、按分数**降序**，取前 20 返回。

**关键点**：这不是机器学习，是**手写权重的线性加权**；因为候选池只有 25 条，"推荐"本质是"在这 25 家里排序"。

## 五、推荐理由从哪来

`rank.py` 里每加一次分就 push 一条中文短语，最后用 `；` 拼起来写进 `reason`——**是规则生成的，不是 AI 写的**。

## 六、缓存与 AI

- 每次请求都会**先删掉该碰面的旧缓存**，再把排好序的 20 家写入 `restaurants` 表。
- **AI 推送**：把规则排序后的前 30 家拼成文本丢给 DeepSeek，要求"挑 20 家、按推荐度排序、写简短理由"，返回纯文本直接展示；没配 `LLM_API_KEY` 时优雅降级（返回一句提示，不影响规则结果）。

## 七、发现 3 个问题（要修告诉我）

1. 🐛 **偏好功能实际上是失效的**：`set_preference` 写入时存的是 **`code`**（`Preference.meetup_id = code`），而 `get_restaurants` 查询用的是 **`m.id`（UUID）** ——两边永远匹配不上，所以「优先/排除品牌」**永远不会生效**。加上前端压根没调用这个接口，功能等于没接上。
2. ⚠️ **候选池太小**：只拉 1 页 25 条、"综合排序"实际是在这 25 条里排；提高推荐质量最直接的办法是**翻页多拉几页**（高德单页 ≤25，可 page 1..4 共 100 条）再排序。
3. ⚠️ **AI 的上下文是硬编码的**：前端传的 `center_name='市中心'`、`prefers='靠近商圈、交通方便、优先连锁品牌、评分高'` 都是写死的，没用真实的商圈名和用户实际筛选条件。
