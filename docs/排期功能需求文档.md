## 0. 背景与目标场景

排期 = 多人协同确认「大概哪天/哪个时段有空」。与现有「碰面」解耦（碰面解决的是**地点**，排期解决的是**时间**）。

两个核心场景（来自需求方）：
1. **周末三天约吃饭**：提前一周发起，时间段约 3 天（如 2026-09-19 ~ 2026-09-21），让大家勾选哪天有空；合并出最适合的一天，再进入「碰面/找吃饭地方」。
2. **约时间出去旅行**：确认旅行天数与出发时间，时间段可能跨多天（如 2026-10-01 ~ 2026-10-07），合并出大家都方便出发/在场的日期窗口。

设计原则（沿用现有项目约定）：
- 匿名身份、免登录（设备 `device_id` / 微信 `openid` 复用现有 `get_current_user`）。
- 分享走 `FRONTEND_BASE` + 前端路由（`share_url`），小程序用 `useShareAppMessage` 转发。
- 数据库变更走 `init_db.py` 幂等建表（新表直接 `create_all`，参考 `Preference`/`Participant` 的 JSON 列用法）。
- 组件风格沿用 `PageContainer` / `Section` / `Icon` / `BottomNav`，橙色主题 `#ff6b35`。

## 3. 数据模型（数据库表 + 字段）

新增 3 张表，全部在 `backend/app/models.py` 定义、`init_db.py` 自动建表（新表无需 `EXTRA_COLUMNS`，直接 `create_all`）。

### 3.1 `schedules`（排期表）
| 字段 | 类型 | 说明 |
|---|---|---|
| id | String(36) PK | uuid |
| code | String(8) unique, index | 分享码（复用 `_gen_code` 逻辑） |
| creator_id | String(36) FK→users.id | 发起者 |
| title | String(128) | 标题 |
| description | Text NULL | 描述 |
| start_date | Date | 时间段开始（含） |
| end_date | Date | 时间段结束（含） |
| granular_hours | Boolean, default False | 是否精确到小时 |
| status | Enum('open','closed') default 'open' | open=可编辑；closed=发起者锁定 |
| created_at | DateTime | |
| closed_at | DateTime NULL | 锁定时间 |
| updated_at | DateTime NULL | 元信息修改时间 |

### 3.2 `schedule_participants`（排期参与者，复用 Participant 结构）
| 字段 | 类型 | 说明 |
|---|---|---|
| id | String(36) PK | uuid |
| schedule_id | String(36) FK→schedules.id | |
| user_id | String(36) FK→users.id NULL | 匿名可空 |
| nickname | String(64) | |
| avatar | String(512) NULL | 微信头像 |
| wechat_id | String(128) NULL, index | 微信 openid |
| availability | JSON NULL | **本人的有空数据**（见 3.4 结构） |
| joined_at | DateTime | |

### 3.3 `schedule_availabilities` —— 不单独建表
本人作答直接存在 `schedule_participants.availability`（JSON），一人一行，编辑即整体 upsert。理由：规模小（天数×槽位×人数），JSON 与现有 `Preference` 列一致，前后端都好处理。

### 3.4 availability JSON 结构
```json
{
  "2026-09-19": {
    "day": "yes",                 // 当天总态：yes|maybe|maybe_not|no（未答=null）
    "slots": {                    // 仅当 schedules.granular_hours=true 时存在
      "09:00-11:00": "yes",
      "11:00-13:00": "maybe",
      "13:00-15:00": "maybe_not",
      "15:00-17:00": "no",
      "17:00-19:00": null,
      "19:00-21:00": null
    }
  }
}
```
- 键为 `YYYY-MM-DD`（区间内每天一个）。
- 4 个可选值：`yes`(应该有空) / `maybe`(可能有空,待确认) / `maybe_not`(可能没空,待确认) / `no`(一定没空)；未答=`null`。
- 非精确到小时时只有 `day`，无 `slots`。

## 4. 后端接口清单（新增 `backend/app/api/schedules.py`）

鉴权复用 `get_current_user`（`X-Device-Id`）；`share_url` 用 `settings.FRONTEND_BASE`。

| 方法 | 路径 | 说明 | 关键入参 / 返回 |
|---|---|---|---|
| POST | `/api/schedules` | 创建排期（同时建发起者参与者+空 availability） | body: title, description, start_date, end_date, granular_hours → `ScheduleOut`（含 code, share_url, my_participant_id） |
| GET | `/api/schedules/{code}` | 详情：meta + 参与者列表 + 我的 availability | → ScheduleOut（participants 含 nickname/avatar/availability 摘要） |
| PATCH | `/api/schedules/{code}` | 修改元信息（标题/描述/时间段/精度，**时间段可后续修改**） | body: 任意可空字段 |
| POST | `/api/schedules/{code}/join` | 加入（昵称/头像/openid） | → ScheduleOut |
| PUT | `/api/schedules/{code}/availability` | **保存本人作答**（核心编辑接口，整体 upsert JSON） | body: `{ "availability": {...} }` → ok |
| GET | `/api/schedules/{code}/merge` | 合并热度：每格各等级计数 + 每参与者明细（供钻取） | → MergeGrid（见第 7 节） |
| POST | `/api/schedules/{code}/close` | 发起者锁定（status→closed） | → ok |
| POST | `/api/schedules/{code}/open` | 发起者重新开启 | → ok |
| GET | `/api/schedules/mine` | 我发起+参与的列表（供列表页） | → List[ScheduleOut] |

`ScheduleOut`（Pydantic，放 `schemas.py`）：id, code, title, description, start_date, end_date, granular_hours, status, creator_id, created_at, participant_count, participants[], share_url, my_participant_id。

## 5. 核心交互：时间选择网格（研究 + 推荐方案）

需求方明确要求：PC/移动都不要一个个点，要**鼠标拖动 / 触屏滑动**批量选择；并要我研究「效率最高、最方便」的样式。

### 5.1 调研结论（业界做法）
- **When2meet / Doodle**：日期×时段网格，拖拽涂抹标记「有空」。最高效、最易学，是多人约时间的黄金标准。
- **Calendly**：单选时隙，不适合「多人各自标注区间」。
- **Apple/Google 日历**：月视图点选，单次选一格，不适合批量。

结论：**采用 When2meet 式网格 + 多级画笔**，最契合「拖一片就标好」的需求。

### 5.2 推荐网格 `ScheduleGridEditor`
- **行** = 区间内的每一天（标签：`09-19 周六`）。区间很长（如 >60 天）时整列纵向滚动，可按周分组。
- **列**（精确到小时时）= 6 个固定时段 + 1 个「全天」快捷列；非精确到小时时只有 1 列（当天整体）。
- 每个单元格 = 彩色方块。
- **画笔调色板 `AvailabilityBrush`**（顶部 4 色 + 橡皮）：
  - 绿=应该有空 / 黄绿=可能有空(待确认) / 黄=可能没空(待确认) / 红=一定没空 / 橡皮=清除。
- **交互**：
  1. **拖拽涂抹（主交互）**：选好画笔后，在网格上按住拖过一片单元格，整片涂成该等级（鼠标拖 / 触屏滑都支持）。对应「周末三天约吃饭」一拖即标 3 天绿。
  2. **点按循环**：单击单元格在 `null→yes→maybe→maybe_not→no→null` 间循环，便于微调单格。
  3. **整行/整列快捷**：点日期标签 = 设当天全部；点时段表头 = 设该时段全区间。
- **自动保存**：编辑后防抖 800ms `PUT /api/schedules/{code}/availability`。
- **只读模式**：`status='closed'` 或非本人查看合并图时禁用涂抹（只展示，点击触发钻取）。

### 5.3 备选（文末 Q3 确认）
- **A（已确认采用）：When2meet 式 4 色画笔 + 拖拽涂抹 + 点按循环。**
- B：日历月视图 + 长按选择（更贴近「看日历」直觉，但批量差）。
- C：逐格点击下拉选择（实现最简单，但最慢，不符合「不要一个个点」）。

## 6. 状态 / 颜色映射 与 合并热度算法

### 6.1 4 个选择等级 → 颜色（已确认采用 5 态模型）
| 等级 | 文案 | 颜色 |
|---|---|---|
| `null` | 未作答（第 5 态，浅灰/白） | 浅灰 `#f3f4f6` |
| `yes` | 应该有空 | 绿 `#22c55e` |
| `maybe` | 可能有空，待确认 | 黄绿 `#a3e635` |
| `maybe_not` | 可能没空，待确认 | 黄 `#facc15` |
| `no` | 一定没空 | 红 `#ef4444` |

> **已确认**：单元格有第 5 个「未作答」态（浅灰/白），与 4 个可选等级并存。
> - 默认新格子 = `null`（浅灰/白），**不是**默认「可能没空」。
> - 这样合并视图里「纯白=大部分不确定」才准确（区分「没人答」与「大家都说可能没空」）。
> - 用户第一次点选时用「画笔」当前色；点按循环顺序：`null → yes → maybe → maybe_not → no → null`。

### 6.2 合并热度图 5 档（见第 7 节 MergeGrid）
按「作答该格的参与者」统计 yes/maybe/maybe_not/no 数量：
- **深绿 `#15803d`**：全部 = yes（大家都一定有空）
- **浅绿 `#86efac`**：yes 占比 ≥ 50% 且 no = 0（大部分有空）
- **浅红 `#fca5a5`**：no 占比 ≥ 50%（大部分没空）
- **深红 `#b91c1c`**：全部 = no（大家都没空）
- **纯白 `#ffffff`**：其余（混合 / 多数未答 = 大部分不确定）

> 阈值「大部分」取 ≥ 50%，可在后端常量统一配置。

### 6.3 钻取 `ScheduleCellDetail`
点某天/某时段 → 底部抽屉列出每个参与者该格选择：`[● 绿] 小明 应该有空` / `[● 黄] 小红 可能没空(待确认)` … 用颜色圆点 + 文字，直观对照。

## 7. 合并接口返回结构（MergeGrid）
`GET /api/schedules/{code}/merge` 返回：
```json
{
  "granular_hours": false,
  "days": ["2026-09-19", "2026-09-20", "2026-09-21"],
  "slots": ["09:00-11:00", ...],   // granular_hours=true 时
  "cells": {
    "2026-09-19": {
      "day": { "yes":2, "maybe":1, "maybe_not":0, "no":0, "bucket":"light_green" },
      "slots": {
        "09:00-11:00": { "yes":2, "maybe":0, "maybe_not":1, "no":0, "bucket":"light_green" }
      }
    }
  },
  "participants": [ { "id":"..", "nickname":"小明", "avatar":".." } ],
  "breakdown": {                  // 钻取明细：day -> slot? -> [{pid, level}]
    "2026-09-19": { "slot?": [ {"pid":"..","level":"yes"} ] }
  }
}
```
前端据此渲染热度图与钻取列表，无需再拉每人原始 JSON。
